# NEXT F CMS v1.0.32 — FazerCards Supplier Funding (P4 RC)

## Scope

v1.0.32 extends the existing Gaming Store Supplier Control Center with production supplier-funding controls for FazerCards. The CMS remains a staff control plane only: provider credentials stay inside the Gaming API Worker and the browser never communicates with FazerCards directly.

## Staff workflow

1. Open `Gaming Store → Suppliers → FazerCards`.
2. Refresh live funding state to retrieve the current FazerCards balance, supported funding methods and recent funding intents.
3. Select a method and amount. Method limits are supplied by the Gaming API from FazerCards and are not hard-coded in the CMS.
4. Create the funding intent. The CMS and Gaming API both enforce idempotency.
5. Complete the payment outside the CMS. Binance Pay remains user-authorized in Binance; crypto methods show only the provider-returned destination/network/memo details.
6. For Binance Pay, enter the Binance Order ID to verify the provider payment.
7. Refresh/reconcile the intent until the provider reports a terminal state.

## Authorization

Funding reads and mutations require both:

- `gaming.suppliers.manage`
- `gaming.finance.manage`

This intentionally separates supplier/catalog administration from financial authority.

## Server-to-server secret

Configure the same dedicated secret on the CMS API Worker and Gaming API Worker:

```bash
npx wrangler@latest secret put GAMING_CMS_SUPPLIER_FUNDING_TOKEN --cwd infrastructure/cloudflare --config wrangler.production.jsonc
```

Do not place this token in Vite variables, browser storage or committed configuration.

## CMS operations

Queries:

- `staff.gaming.supplier.funding.snapshot.get`
- `staff.gaming.supplier.funding.payment.get`

Commands:

- `staff.gaming.supplier.funding.create`
- `staff.gaming.supplier.funding.verify`

The CMS Worker forwards only the exact supplier-funding command to `gaming-api.nextf.lk` and preserves the staff principal, request correlation and idempotency boundary.

## Security properties

- `FAZERCARDS_API_KEY` remains a Gaming API Worker secret.
- No Binance account API key, secret, wallet seed phrase or private key is introduced.
- The CMS does not support arbitrary payout/wallet destinations.
- The Binance Order ID is forwarded only for provider verification and is not stored in CMS audit details.
- Browser projections exclude internal idempotency-key hashes.
- All financial mutations are permission-gated, idempotent and audited.

## Data model

No CMS D1 migration is required. Canonical funding records live behind the Gaming API supplier-funding namespace using the existing shared durable document infrastructure.

## Rollback

If supplier funding must be disabled, roll the CMS back to v1.0.31 and remove/rotate `GAMING_CMS_SUPPLIER_FUNDING_TOKEN`. Existing canonical funding records remain in shared D1 for audit/reconciliation and are not deleted by rollback.
