# NEXT F CMS V0.18.0 — Shared Backend/API Boundary

## 1. Purpose

V0.18.0 creates the application boundary that the **internal Admin CMS**, the future **separate Customer Workspace**, trusted **managed-site adapters**, controlled **Demo Environments**, and selected low-trust **nextf.lk public submissions** will use.

This release does **not** claim that a production API server is already deployed. The current CMS remains a source-only/browser-backed product prototype. V0.18 adds production-oriented TypeScript contracts, authorization rules, idempotency semantics, projections, audit contracts and adapter interfaces plus a local proof harness. Production transport, database repositories, identity providers, secrets and adapter credentials remain deployment work.

This distinction is intentional. The architecture must stabilize before Cloudflare Workers/D1/R2/Queues or another infrastructure stack is allowed to dictate authorization or domain behavior.

---

## 2. Governing architecture

The approved scope requires:

- the internal Admin CMS to remain staff-only;
- the Customer Workspace to be a separate frontend;
- staff and customers to view controlled projections of the same authoritative business entities;
- customer authorization to be enforced by the backend, not UI visibility;
- Demo Access to remain isolated from real customer tenancy;
- managed websites to obey Contracts/Site Manifest/capability policy;
- `nextf.lk` public writes to enter controlled APIs instead of internal stores/databases directly.

V0.18 therefore places one governed backend boundary between user-facing clients and authoritative domain operations.

```text
Internal Admin CMS
      │ staff principal
      │
      ├──────────────┐
      │              │
Customer Workspace   │
      │ customer     │
      │ principal    │
      │              ▼
Demo Workspace ───► Shared V1 Backend Boundary ◄── Managed Site Adapter/Service
      │ demo             │                         service principal
      │ principal        │
                        │
nextf.lk public forms ──┘
      public ingress

Backend boundary
      │
      ├─ NEXT F Platform identity / governance
      ├─ NEXT F Digital authoritative entities
      ├─ Customer Workspace memberships
      ├─ Website Platform policy/workflows
      └─ connected-site adapter contracts
```

The public website content-delivery plane is deliberately not made an internal Admin/Customer API. Public site content should be delivered through the website/runtime publishing architecture governed by the Site Contract, not by exposing internal business APIs.

## 3. Trust zones / principals

### 3.1 Staff principal

A staff principal contains:

- Platform staff user ID;
- NEXT F organization context;
- resolved staff permissions;
- authentication assurance.

Staff actions still require operation-specific permissions. Being a staff user is not sufficient by itself.

### 3.2 Customer principal

A customer principal is deliberately stronger than `accountId`.

It contains:

- NEXT F Account ID;
- Customer Organization ID;
- Customer Workspace ID;
- exact active Membership ID;
- Customer Role ID;
- authentication assurance.

The server mints this context after authentication and membership resolution. A browser cannot become authorized by sending a different `workspaceId`.

The backend compares every workspace-scoped customer request with the workspace/organization already embedded in the principal. Any mismatch fails closed.

### 3.3 Demo principal

A demo principal contains only:

- Demo Access Request ID;
- Demo Environment ID;
- environment key;
- expiry;
- authentication assurance.

The authorization layer requires the environment to be:

- active;
- unexpired;
- `synthetic_only`.

Demo principals are explicitly denied production Customer Workspace scope.

### 3.4 Public principal

`nextf.lk` requires a low-trust public ingress for selected writes such as lead submission and Demo Access Request submission.

A public principal is **not a customer identity**. It contains:

- server-established source (`nextf.lk` or unknown);
- abuse-protection status;
- anonymous assurance.

Registered V1 public commands require:

- source to be the trusted `nextf.lk` public route as determined by the server/edge path;
- no Customer Workspace scope;
- an idempotency key;
- verified rate-limit/abuse-protection evidence before business processing.

Submitting a lead or demo request never creates Customer Workspace access.

### 3.5 Service principal

Service principals are for server-to-server operations such as managed-site adapter receipts.

They use explicit scopes such as:

- `managed-site:revision:observe`;
- `managed-site:change:receipt`;
- `managed-site:publish:receipt`.

They cannot impersonate a customer workspace.

## 4. Request context

Every backend operation receives a server request context containing:

- API version;
- request ID;
- correlation ID;
- resolved principal;
- issue timestamp;
- idempotency key when required.

Client-supplied actor labels are not trusted as identity.

Request/correlation IDs are carried into audit and execution evidence so a staff/customer action can be traced through API, workflow and adapter operations.

---

## 5. Query/command contract

V0.18 introduces a V1 operation registry rather than allowing arbitrary frontend-to-store calls.

### Queries

Queries are read operations. Examples include:

- `staff.workspace.get`;
- `staff.workspace.activity.list`;
- `staff.website-platform.queue.list`;
- `customer.workspace.get`;
- `customer.projects.list`;
- `customer.sites.list`;
- `customer.approvals.list`;
- `customer.billing.summary`;
- demo safe-data queries.

### Commands

Commands mutate authoritative workflow/domain state. Examples include:

- provisioning review/activation;
- membership invitation;
- customer change submission;
- staff change review/approval/rejection;
- publication request/approval;
- customer support/approval responses;
- public lead/demo-request intake;
- managed-site revision/application/publication evidence.

Every registered mutation currently requires an idempotency key.

This operation list is an application boundary, not the canonical website Contract Registry. Website-specific capability/permission/API IDs remain sourced from `contracts.nextf.lk` and the validated Site Manifest flow from V0.15/V0.16.

## 6. Server-side authorization order

For a V1 operation the backend must evaluate, in order:

1. Is the operation registered?
2. Is the principal kind allowed?
3. If it is a command, is idempotency present?
4. For staff: does the staff principal have the required Platform/Digital permission?
5. For customer: does requested workspace scope exactly equal the principal scope?
6. Is the Customer Workspace active/read-only as applicable?
7. Does the exact principal Membership still exist, remain active and remain accepted?
8. For demo: is the exact synthetic environment active and unexpired?
9. For public: is it a permitted public route with abuse protection and no workspace scope?
10. For service: are the explicit service scopes present?
11. For website capability mutations: V0.16 effective authorization must still evaluate Contract → Site → entitlement → role permission → resource state → field/security policy.
12. For V0.17 workflows: revision/concurrency/approval/publishing preconditions still apply.

The API boundary does not replace V0.16/V0.17. It is the server entry point that must invoke them.

## 7. Workspace tenancy rule

The central tenancy rule is:

> A Customer Workspace ID sent by a browser is routing input, not authorization evidence.

The customer principal already contains the authorized organization/workspace/membership tuple.

A customer request for a different workspace or organization is denied even if:

- that workspace exists;
- the user knows the ID;
- the UI accidentally exposes the ID;
- another endpoint would otherwise return the resource.

This prevents horizontal cross-tenant access by construction.

## 8. Idempotency

All V1 commands require an `Idempotency-Key`.

An idempotency claim is bound to:

- key;
- command name;
- authenticated principal fingerprint;
- normalized request fingerprint;
- state;
- expiry;
- final response reference when complete.

### Outcomes

- **claimed** — caller owns the first execution;
- **replay** — the exact same authenticated command has already been seen;
- **conflict** — the key is being reused with a different principal/command/payload.

A completed replay returns the stored response reference rather than re-running the mutation.

The included `MemoryIdempotencyRepository` is explicitly development-only. Production requires a durable atomic repository so two Worker instances cannot both win the same claim.

## 9. Staff vs customer projections

The same authoritative business entity should not be copied into independent staff/customer databases merely because the UI differs.

V0.18 creates separate DTO concepts:

- `StaffWorkspaceProjection`;
- `CustomerWorkspaceProjection`;
- `DemoWorkspaceProjection`.

### Staff projection may include

- client linkage;
- provisioning status;
- attachment IDs;
- membership counts;
- internal operational flags.

### Customer projection contains only customer-safe context

- own workspace identity/status;
- own membership/role reference;
- attached project/service IDs that are customer-visible;
- connected managed-site summaries;
- whether current customer capability projection is ready.

Customer projections must not expose:

- staff notes;
- internal audit detail;
- provider credentials;
- secrets/API keys;
- infrastructure configuration;
- unrestricted deployment settings;
- hidden Contract/Admin metadata.

### Demo projection

Demo projection reads only the synthetic environment record. It does not join real Customer Workspace data.

## 10. Managed-site adapter interface

V0.17 created governance around external website revisions but intentionally left the real connected-site executor for later.

V0.18 defines the adapter interface that production must implement.

### Required operations

- observe authoritative resource revision;
- apply an approved change;
- publish a target revision;
- check managed-site health.

### Required context

Every adapter request carries:

- Site Connection ID;
- current Contract/Manifest validation evidence ID;
- correlation ID;
- server-side credential reference.

Secrets themselves are never returned to Admin CMS or Customer Workspace clients.

### Optimistic concurrency

Apply requests pin:

- resource/capability;
- expected base revision;
- expected base content hash;
- approved field changes.

Publish requests pin:

- resource/capability;
- exact target revision;
- exact target content hash.

Successful calls return adapter receipts. V0.17 workflow state must not be marked applied/published unless the appropriate receipt exists.

## 11. Audit contract

Backend audit records include:

- action;
- principal type and server identity;
- organization/workspace context where applicable;
- target;
- outcome;
- request ID;
- correlation ID;
- detail and timestamp.

Authorization denial, command completion and command failure are appropriate audit events for sensitive operations.

Customer-visible activity can later be projected from shared event infrastructure, but internal audit detail remains filtered.

## 12. `nextf.lk` integration boundary introduced now

V0.18 registers two deliberate public write categories needed by the existing architecture plan:

### `public.lead.submit`

Purpose: route website enquiries into a governed NEXT F Digital intake path.

Rules:

- anonymous/public, not Customer Workspace;
- abuse protection required;
- idempotent;
- creates/updates the authoritative Digital lead workflow through backend logic;
- never grants account/workspace access;
- frontend never writes directly to D1/internal tables/browser CMS stores.

### `public.demo-access.request`

Purpose: submit a prospect Demo Access Request.

Rules:

- public low-trust ingress;
- abuse protection required;
- idempotent;
- produces a request that enters staff review;
- never activates a Demo Environment automatically.

Exact integration into live `nextf.lk` routes/components remains Phase 8 and must be based on the real live-site source, not guessed.

## 13. What V0.18 intentionally does not implement

V0.18 does not claim completion of:

- deployed HTTP/API transport;
- Cloudflare Worker router;
- D1 production repositories/migrations;
- staff Cloudflare Access adapter;
- customer production identity/session/recovery adapter;
- production rate-limit/Turnstile/abuse implementation;
- durable distributed idempotency;
- server secrets/KMS;
- email provider;
- queues/workflows;
- managed-site adapter credentials;
- real connected-site adapter implementations;
- Customer Workspace frontend;
- exact live `nextf.lk` route/component wiring;
- public content-delivery API.

Those are later phases. Keeping them explicitly pending prevents a browser mock from being mistaken for production security.

## 15. Local proof harness

`src/services/backend/localPrototype.ts` bridges existing V0.13–V0.17 stores only for architecture verification.

It can:

- mint a local staff principal from the existing staff session;
- mint a customer principal only from a verified Account + active accepted Membership + active/read-only Customer Workspace + active customer Organization;
- mint a demo principal only from an active unexpired synthetic environment;
- create separate staff/customer/demo projections;
- expose production-readiness flags.

This harness is not a production backend adapter.

## 16. Production implementation requirements

When Phase 9 replaces browser repositories, the production API implementation must preserve these contracts.

At minimum:

- transport authenticates before handlers run;
- principal is server-derived;
- tenant/workspace scope never trusts browser input alone;
- durable idempotency claims are atomic;
- authorization denials are fail-closed;
- audit events are append-oriented;
- secrets remain server-side;
- customer projections filter fields server-side;
- public ingress is rate limited and abuse protected;
- adapter receipts are validated before workflow completion;
- request/correlation IDs survive downstream calls;
- errors use stable problem codes rather than leaking internal stack/data.
