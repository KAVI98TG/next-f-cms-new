# NEXT F CMS V0.24.0 — Production Go-Live P1 · Durable Backend

## Purpose

P1 replaces browser persistence as the production source of truth for the internal CMS. The existing synchronous domain stores remain stable for the UI, but their storage boundary now switches by runtime mode:

- `local-prototype`: local browser adapter for development fixtures and rapid offline prototyping.
- `production-api`: Cloudflare Worker staff API backed by D1 durable documents.

Production mode fails closed if the backend cannot initialize. Seed arrays are not promoted into production records when D1 has no document for a key.

## Production data path

1. `src/main.tsx` awaits the durable-state bootstrap before rendering the CMS.
2. `durableStorage.ts` requests `staff.state.snapshot.get` and builds an in-memory working cache.
3. Existing Platform, Digital, Gaming Store, Software, Help Center and Website Platform stores read/write through the shared durable boundary.
4. Mutations call `staff.state.document.put` or `staff.state.document.delete` with a unique idempotency key and the last observed document version.
5. The Worker verifies the Cloudflare Access JWT, resolves an active `staff_identity_bindings` row, applies server-side permission rules, claims idempotency in D1, writes with optimistic concurrency and records an audit event.
6. Conflicting writes fail with HTTP 409 and the frontend emits a durable-state error event rather than silently overwriting newer data.

## D1 responsibilities

The P1 path uses the existing core migration tables:

- `app_documents` — durable JSON documents with namespace, version and soft-delete support.
- `idempotency_records` — command replay/conflict protection bound to command, staff principal and request hash.
- `audit_events` — immutable mutation evidence.
- `staff_identity_bindings` — server-side mapping from verified Cloudflare Access subject to CMS staff identity and permissions.

P1 deliberately uses a coarse document-per-existing-store-key bridge. This is a migration-safe production persistence layer for the current synchronous UI contracts, not a claim that every business domain has already been normalized into final relational tables.

## Staff API handlers connected in P1

Queries:

- `staff.state.snapshot.get`
- `staff.state.document.get`
- `staff.workspace.activity.list`
- `staff.website-platform.queue.list`

Commands:

- `staff.state.document.put`
- `staff.state.document.delete`

Other semantic operation names in the shared backend contract remain explicit future handlers and are not falsely reported as implemented.

## Browser storage boundary

Operational business source files no longer call `window.localStorage` directly. Direct browser storage is restricted to:

- theme preference;
- the temporary local-development staff session selector, which P2 will replace for production;
- the local-prototype branch inside the shared durable-storage adapter.

Data Management export/import now targets the shared durable storage boundary and uses the `nextf-cms-durable-backup` schema.

## Security properties added

- Cloudflare Access cookie transport via `credentials: include`.
- Access subject must exactly match an active D1 staff binding.
- Permission-filtered bootstrap; unauthorized documents are not returned.
- Permission checks repeat on every durable mutation server-side.
- Mandatory command idempotency.
- Optimistic concurrency by D1 document version.
- Mutation audit evidence with request/correlation IDs.
- Production startup fails closed if D1/API/identity authorization is unavailable.

## Intentionally deferred after P1

P1 does **not** complete production identity UX. `SessionProvider` still contains the local-development session/assume-user mechanism. P2 must replace that frontend identity model with the verified production principal and disable local impersonation outside local mode.

P1 also does not create actual Cloudflare resources, bind production secrets, execute the D1 migration remotely, deploy the Worker, or prove real browser/CI acceptance. Those remain deployment/evidence work. Managed-site semantic adapters are also outside this bridge.
