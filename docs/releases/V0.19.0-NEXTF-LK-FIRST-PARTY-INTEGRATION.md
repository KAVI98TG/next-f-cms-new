# V0.19.0 — `nextf.lk` First-Party Integration

## 1. Purpose

V0.19.0 connects the NEXT F Digital public-site architecture to the governed backend boundary introduced in V0.18 without weakening the separation between the public website, the internal Staff CMS, Customer Workspaces, Demo Environments, or managed customer sites.

The approved scope identifies **`nextf.lk` as the main public website for NEXT F Digital**. It represents NEXT F Digital services, customer acquisition, pricing/resources, projects/case studies and other public business content. That makes it a first-party surface of NEXT F Digital, but it does **not** make a browser request trusted and it does **not** make the site a Customer Workspace tenant.

V0.19 therefore establishes a dedicated first-party integration model:

```text
nextf.lk
  │
  ├── safe public reads ──────► Public Projection API
  │                              │
  │                              ├── explicitly published Services
  │                              ├── explicitly published Case Studies
  │                              └── explicitly published Help resources
  │
  ├── lead/contact writes ────► public.lead.submit
  ├── demo request writes ────► public.demo-access.request
  └── conversion telemetry ───► public.conversion.track
                                 │
                                 ▼
                     Shared V1 Backend Boundary
                                 │
                         authoritative systems
```

The public site never reads Staff CMS browser stores, future D1 tables, Customer Workspace records, credentials, or internal operational entities directly.

---

## 2. Source limitation and no-guessing rule

The current execution environment cannot resolve `nextf.lk`, and the V0.18 source handoff does not contain the public-site source repository.

V0.19 therefore **does not invent live paths, page names, components or frontend route wiring**.

The staff system registers the required logical public-site surfaces:

- lead/contact form;
- Demo Access Request;
- account registration entry;
- Customer Workspace sign-in entry;
- services;
- case studies;
- Help/resources;
- conversion events.

Every route begins `unmapped`.

A route can only become `verified` when staff records:

1. an actual `nextf.lk` URL/path; and
2. source/component evidence proving the binding.

The route verifier rejects URLs belonging to another hostname. This keeps Phase 8 faithful to the master-plan requirement that route/component mapping come from the real public-site source or a verifiable live crawl.

## 3. First-party site identity

V0.19 introduces a dedicated first-party record with these semantics:

- Site key: `nextf-digital-main`
- Host: `nextf.lk`
- Business: NEXT F Digital
- Owning organization: `org_nextf`
- Tenancy: `first_party`
- Delivery mode: `projection_api`
- Direct internal database access: `false`

This is deliberately **not** represented as:

- a fake Digital Client;
- a Customer Organization;
- a Customer Workspace;
- a customer Membership;
- a customer Site Connection.

Customer tenancy remains for actual customer relationships. The NEXT F main site is a NEXT F-owned public acquisition/delivery surface.

## 4. Public publication boundary

Internal business data does not become public merely because it exists.

V0.19 adds `PublicProjectionPublicationRecord` with:

- authoritative source kind;
- authoritative source ID;
- separate public ID;
- stable public slug;
- `draft / published / withdrawn` lifecycle;
- explicit `publicFields` allowlist;
- optional public title/summary overrides;
- publisher and timestamps.

Supported first-party projection kinds are currently:

- `service`
- `case_study`
- `help_article`
- `help_faq`

The projection record is configuration/evidence. It does not duplicate the authoritative domain entity.

### Service exposure

An internal Service Package is eligible only when:

- it still exists;
- it is active;
- there is an explicit published public-projection record.

Fields such as family, description, billing model, price and duration are exposed only when listed in `publicFields`.

Price is particularly deliberate: an internal base price does not leak into the public API unless `basePrice` is allowlisted for that publication.

### Case-study exposure

An internal Digital Project may become a public case study only when:

- the project is `completed`;
- staff deliberately creates/publishes a case-study projection;
- public title and public summary are present.

The case-study projection does **not** expose:

- client ID;
- project value;
- milestones;
- internal progress history;
- invoices/subscriptions;
- staff notes;
- customer workspace information.

No current seed project qualifies as a case study automatically. This is intentional.

### Help content exposure

Help articles/FAQs are eligible only when:

- the source itself is already `published`;
- audience is `all` or `digital`;
- staff also publishes a first-party projection.

A Help Center record being published to Help Center audiences is not automatically permission for `nextf.lk` delivery.

### Withdrawal

Withdrawal changes public delivery state only. The source Service/Project/Help record is not deleted or modified.

## 5. Public read operations

V0.19 extends the V1 operation registry with:

- `public.site.bootstrap.get`
- `public.services.list`
- `public.case-studies.list`
- `public.help.list`

These operations use the existing `public` trust zone and carry no Customer Workspace scope.

### Bootstrap projection

The bootstrap read model contains only safe first-party information, including account-registration and Customer Workspace sign-in entry points when those routes have real verified evidence.

Until source evidence exists, the bootstrap response keeps them `unmapped` rather than inventing URLs.

### Public content projections

Public Services, Case Studies and Help resources are separate DTOs rather than internal record serialization.

The server implementation must serialize those DTOs directly. It must not fetch an internal entity and remove a few fields at the frontend.

## 6. Lead/contact ingress

V0.18 registered `public.lead.submit`; V0.19 defines the first-party mapping into NEXT F Digital Sales.

A public lead submission can contain:

- contact name;
- email;
- company;
- phone;
- optional public service ID;
- message/enquiry detail;
- privacy acknowledgement;
- optional marketing consent;
- source-surface context.

### Important rules

- Email is normalized/validated server-side.
- Privacy acknowledgement is required.
- A selected service must map through an **already published public Service projection**.
- A general contact enquiry is allowed without choosing a service.
- General enquiries cannot be qualified into an Opportunity until staff assigns an actual NEXT F Digital service.
- Public leads enter the existing authoritative Digital Lead repository.
- Public source is recorded as `nextf.lk`.
- Enquiry text is bounded before storage.
- Privacy and optional marketing consent timestamps are recorded separately.

The `DigitalLead` model is therefore extended with optional public-ingress evidence fields. Staff-created leads may continue to use the existing required-service UI workflow.

### No automatic customer provisioning

A public lead does not create:

- a NEXT F Account;
- a Digital Client;
- a Customer Organization;
- a Customer Workspace;
- a Membership;
- a managed-site connection.

It is a sales intake record only.

## 7. Demo Access Request ingress

`public.demo-access.request` maps to the existing governed Demo Access Request lifecycle.

V0.19 requires:

- name;
- email;
- company;
- privacy acknowledgement.

Successful ingress calls the same authoritative `websitePlatformStore.submitDemoRequest()` used by the Staff Website Platform model.

The resulting state remains:

`submitted`

It still requires staff review, approval, isolated-environment provisioning and activation through V0.14 governance.

Public submission cannot create or activate a Demo Environment.

## 8. First-party conversion events

V0.19 registers a deliberately small business-event vocabulary:

- `lead_submitted`
- `demo_access_requested`
- `account_entry_clicked`
- `workspace_sign_in_clicked`
- `service_interest`
- `case_study_viewed`

These are NEXT F first-party business telemetry definitions. They are **not** invented `contracts.nextf.lk` website capability IDs.

### PII rule

Every event has:

- an allowlist of acceptable payload keys;
- an explicit PII denylist.

Direct fields such as name, email, phone, company and message are forbidden in conversion payloads.

Unknown payload keys fail closed rather than being silently accepted.

Allowed values must be scalar.

This design enables downstream GA4/Ads/Meta/other analytics adapters later without turning the event stream into a secondary PII database.

`public.conversion.track` is registered as an idempotent public command and remains subject to the V0.18 public abuse-protection requirement.

## 9. Account and Customer Workspace entry points

The public site will eventually expose deliberate entry links for:

- account registration;
- Customer Workspace sign-in.

V0.19 deliberately does **not** invent these route URLs because:

1. the public-site source is unavailable here; and
2. the production customer identity/session adapter is a later infrastructure concern.

The bootstrap projection will expose a URL only after the route binding is verified from real source evidence.

A link to account registration is not authorization. Registration still follows the approved identity model and grants no Customer Workspace entitlement by itself.

## 11. Backend boundary changes

The V1 registry now contains the following public operations:

### Queries

- `public.site.bootstrap.get`
- `public.services.list`
- `public.case-studies.list`
- `public.help.list`

### Commands

- `public.lead.submit`
- `public.demo-access.request`
- `public.conversion.track`

All public operations remain non-workspace scoped.

All public commands remain idempotent.

The V0.18 authorizer still requires:

- source established as `nextf.lk` by the server/edge route;
- no Customer Workspace scope;
- verified abuse-protection evidence for mutation commands.

The public browser must not be allowed to self-assert a trusted source header in the production transport.

## 12. Production transport requirements

V0.19 is still source-level architecture plus local proof. Production adapters must preserve these rules.

A recommended Cloudflare shape is:

```text
Browser
  │
  ▼
nextf.lk frontend / edge
  │
  ├── GET public projections ─────► cacheable public API
  │
  └── POST public commands ───────► edge validation
                                      ├── rate limit
                                      ├── Turnstile / bot evidence as appropriate
                                      ├── body-size limits
                                      ├── schema validation
                                      ├── server-derived source
                                      ├── idempotency
                                      └── V1 backend command
```

The exact edge/Worker code belongs to the production-infrastructure phase.

---

## 13. Caching and public delivery

When production transport is implemented:

- Service/Case Study/Help reads may use edge caching.
- Cache keys must be public-projection-specific, not internal entity URLs.
- Withdrawal/publication must produce cache invalidation or short bounded TTL behavior.
- ETag/revision metadata should be added to projection responses.
- No customer-specific/private response should share the public cache plane.

V0.19 does not yet claim a production cache adapter.

---

## 14. Security properties

V0.19 preserves these security properties:

1. `nextf.lk` has no Customer Workspace scope.
2. `nextf.lk` does not query internal CMS tables directly.
3. A public Service is explicitly published, not inferred from `active=true`.
4. A completed Project is not automatically a public case study.
5. Public help content requires a second deliberate projection decision.
6. Public writes go through backend commands.
7. Public mutation commands require abuse protection.
8. All public mutation commands require idempotency.
9. Conversion payloads reject direct PII.
10. Route binding cannot be marked verified without source/component evidence.
11. Account registration does not grant Customer Workspace access.
12. Demo request submission never provisions an environment automatically.

## 17. Acceptance criteria

V0.19 is complete at the CMS/backend architecture level when:

- `nextf.lk` has a first-party identity separate from Customer Workspace tenancy;
- public content comes only from explicit safe projections;
- service pricing cannot leak unless explicitly allowlisted;
- case studies require completed source projects and public copy;
- Help resources require deliberate exposure;
- public lead intake lands in authoritative Digital Sales;
- general leads can exist without premature service assignment;
- Demo requests enter the existing governed Demo lifecycle;
- conversion payloads are allowlisted and PII-rejecting;
- public read/query operations are registered;
- public mutations remain idempotent/abuse protected;
- route/component wiring remains blocked until real evidence exists;
- all historical QA remains green.

## 19. Final hardening notes

Before packaging, the first-party integration received four additional hardening changes:

1. **Public seed exposures are draft by default.** We cannot verify live `nextf.lk` content from this environment, so no seeded Service/Help item is implicitly treated as currently public.
2. **Public API handlers use the shared boundary for principal rejection.** They do not pre-throw before authorization, so denied calls use the same standardized problem/audit path as every other V1 operation.
3. **Public lead auditing uses System identity.** A public website submission is no longer mislabeled as an Admin-created lead.
4. **Existing browser data migrates the old main-domain placeholder.** `dom_main` values stored as `nextf.com.lk` normalize to `nextf.lk` when the Platform domain inventory is read.

V0.19 also adds `src/services/backend/publicSiteApi.ts`, which provides the concrete boundary-level handlers for the four public queries and three public commands while remaining transport-agnostic.
