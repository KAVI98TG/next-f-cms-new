# NEXT F CMS V0.12.0 — Website Platform Foundation

## Purpose

V0.12.0 starts the controlled upgrade from the completed V0.11.0 internal CMS into the Platform + NEXT F Digital architecture defined by `NEXT-F-CMS-SCOPE-AND-ARCHITECTURE-DIRECTION.md`.

This release does **not** build the separate Customer Workspace frontend. It adds the internal staff-side foundation required to provision and govern that future application without weakening the existing staff/customer boundary.

## Architecture decisions enforced in this release

1. The existing CMS remains the private Staff / Platform Admin surface.
2. The Customer Workspace remains a separate customer-facing application.
3. A NEXT F Digital client record is not a customer identity or authorization grant.
4. A Customer Workspace is an explicit provisioned entity, not a boolean on a client.
5. Workspace provisioning starts in `requested` state and does not grant customer access.
6. Demo Access has a separate lifecycle and is not a real customer workspace flag.
7. A managed website connection belongs to a specific Customer Workspace and Digital client.
8. A site and workspace must belong to the same Digital client before they can be connected.
9. Website connections are pinned to Contract Version `1.0.0` and expect `nextf.site.json`, as documented by the repository's contract integration guide.
10. Contract-specific module/capability/permission metadata remains fail-closed until an actual Registry snapshot and Site Manifest can be resolved and validated.
11. The old single-email Client Portal shortcut is no longer exposed as the customer-access control in the Clients UI.
12. Existing local data remains untouched so a later migration can be explicit and reversible.

## Added

### NEXT F Digital → Website Platform

New route:

`/next-f/website-platform`

The first staff control center contains:

- Customer Workspace provisioning summary.
- Managed Site Connection summary.
- Contract pin and Site Manifest readiness.
- Demo Access request lifecycle.
- Staff/customer architecture boundary reminders.
- Fail-closed warning when the canonical registry is not locally resolved.

### Customer Workspace records

A real customer workspace has its own record and lifecycle:

- `requested`
- `provisioning`
- `active`
- `read_only`
- `suspended`
- `closed`

This record is linked to a NEXT F Digital client but does not duplicate the client.

Account identity, customer membership, customer roles and entitlements are deliberately not faked in this release. They are the next foundation phase.

### Managed site connection records

A managed site connection records:

- Digital Site ID.
- Customer Workspace ID.
- Contract Version.
- Site Manifest filename.
- Manifest validation state.
- Connection lifecycle.

The implementation refuses a connection when the Digital Site and Customer Workspace do not belong to the same client.

The default manifest state is `unverified`. The CMS does not claim that a contract is valid until the Registry and manifest can actually be validated.

### Demo Access records

Demo requests are separated from real customer workspaces. Supported lifecycle values are:

- `submitted`
- `under_review`
- `approved`
- `rejected`
- `active`
- `expired`
- `revoked`
- `extended`

Approving a demo request does not create or convert a production Customer Workspace.

### Permissions

New staff permission:

`digital.website-platform.manage`

The Digital Manager role receives the permission through the existing role-normalization mechanism. Super Admin receives it through the canonical permission catalog.

### Client 360 safety change

The previous `Client portal access` controls allowed staff to invite, activate, suspend and re-invite a single email directly from a Digital client record.

That control conflicts with the approved architecture because it collapses:

- identity,
- customer organization,
- workspace,
- membership,
- entitlement,
- provisioning,
- and authorization

into one client/email shortcut.

The Client 360 panel now shows Customer Workspace status and routes staff to Website Platform management instead. Legacy portal data is not deleted in V0.12.0.

## Deliberately deferred

V0.12.0 does not invent or prematurely implement:

- Customer identity registration.
- Customer authentication sessions.
- Account verification/recovery.
- Workspace memberships.
- Customer role definitions.
- Customer permission IDs.
- Service entitlements.
- Capability-policy resource IDs.
- Field-level policies.
- Change request / approval persistence.
- Contract Registry resolver.
- Manifest validation engine.
- Customer CMS resource editors.
- Public website delivery APIs.
- Production D1/R2/Workers infrastructure.

Those are subsequent phases in the master upgrade plan.

## Backward compatibility

Existing V0.11.0 stores are not mutated. V0.12.0 introduces new local keys for its new records. The legacy portal store remains available for migration work but is no longer presented as the target customer authorization model.

## QA rule

Every existing V0.11.0 regression suite must continue to pass. V0.12.0 adds `npm run check:website-platform` as an additional architecture gate.
