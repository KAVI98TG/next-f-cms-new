# V0.17.0 — Change Requests, Approvals, Revisions + Publishing Governance

## Purpose

V0.17.0 turns the V0.16 authorization outcomes `change_request`, `publish_request`, and `direct_publish` into explicit governed workflows while preserving the approved NEXT F architecture:

- the internal CMS remains staff-only;
- the Customer Workspace remains a separate application;
- connected websites remain authoritative for website resource content/revisions;
- the CMS stores governance records, evidence, proposals, review decisions, and adapter receipts rather than becoming a second copy of website content;
- editing, approval, application, and publishing remain distinct actions;
- stale proposals fail closed instead of overwriting newer resource state.

## 1. New managed-resource revision evidence model

V0.17 introduces `ManagedResourceRevisionEvidenceRecord` and `ManagedResourceHeadRecord`.

These records do **not** duplicate the website's resource body as an internal CMS content table. They record the connected site's externally reported:

- Site Connection;
- canonical Capability ID;
- resource identifier;
- external revision identifier;
- content hash;
- Site validation evidence ID;
- observation/application source;
- evidence timestamp.

The head record is only the latest known authoritative revision reference used for optimistic concurrency checks. Revision evidence is tied to the exact Site Contract/Manifest validation cycle; after Site revalidation, an old head cannot authorize customer mutation or publishing until the resource is observed again under current evidence. Re-observing the same external revision ID with a different content hash is treated as an immutability violation.

`observeAuthoritativeRevision()` is the adapter-facing ingestion boundary for future website APIs. It requires a connected Site with a current valid canonical Contract projection.

## 2. Customer change request model

`CustomerChangeRequestRecord` captures:

- Customer Workspace membership;
- requester account derived from membership;
- Site Connection;
- canonical capability;
- target resource;
- explicit base revision ID and content hash;
- proposed field-level changes;
- workflow status;
- timestamps;
- resulting revision when an approved change is later applied.

The proposal is separate from authoritative/published state.

A change request can only be created when V0.16 re-evaluates every proposed canonical field and returns the `change_request` execution path. A `direct_mutation` decision is not silently converted into an approval workflow, and a denied/read-only field cannot be submitted.

## 3. Change lifecycle

Implemented lifecycle:

```text
submitted
   ↓
in_review
   ├── changes_requested
   │      └── customer submits a new superseding proposal
   ├── rejected
   ├── conflict
   └── approved
          ↓
     adapter application receipt
          ↓
        applied
```

Important rules:

- only a newly submitted proposal can enter review;
- a `changes_requested` proposal is not re-reviewed in place; the customer must create a new superseding proposal, preserving the old evidence history;
- reviewer change requests and rejection require notes;
- approval requires the authoritative head revision to still match the proposal base revision;
- approval **does not** mutate the website;
- approval **does not** publish;
- application requires an explicit connected-site adapter receipt;
- application uses optimistic concurrency against the expected base revision;
- resulting revision ID and content hash become immutable revision evidence after successful adapter confirmation.

## 4. Review evidence

`ChangeReviewEventRecord` records immutable workflow events such as:

- submitted;
- review started;
- changes requested;
- approved;
- rejected;
- conflict;
- applied.

Each event records actor type/ID, base revision, current revision where applicable, review note, and resulting revision where applicable. The active request also records its current staff reviewer and review-start timestamp for staff queue ownership.

Platform Audit receives the major business/security events in addition to the workflow-specific evidence history.

## 5. Concurrency and conflict detection

V0.17 enforces stale-revision protection at several boundaries:

1. customer submission requires the declared base revision to match the current observed head;
2. starting review checks the head again;
3. approval checks the head again;
4. application receipt checks the optimistic-concurrency base again;
5. observing a new authoritative revision automatically moves open proposals based on an older revision to `conflict`;
6. publication requests targeting an old revision also move to `conflict`;
7. Site Contract/Manifest revalidation moves pending change/publication workflows created under older validation evidence to `conflict`.

No workflow silently rebases or overwrites a proposal.

## 6. Application receipts

`ChangeApplicationReceiptRecord` is the future website-adapter evidence boundary.

A receipt requires:

- approved change request;
- adapter receipt ID;
- expected base revision matching both the request and current head;
- resulting external revision ID;
- resulting content hash;
- applying actor/service identity.

Only after this receipt is recorded does the change request enter `applied` and the managed-resource head advance to the resulting external revision.

This deliberately leaves actual connected-site mutation to a future adapter/API phase.

## 7. Publishing governance

Publishing is implemented as a second workflow rather than a side effect of change approval.

`submitPublishRequest()` re-runs the V0.16 customer authorization evaluator with `operation: "publish"`.

Possible V0.16 outcomes are handled as follows:

- `deny` — no publication request is created;
- `publish_request` — creates a staff-approval publication request;
- `direct_publish` — creates a direct-authorized request that may proceed to the publishing adapter without staff review.

Both staff-approved and direct-authorized publication still require a separate execution receipt before being recorded as published.

## 8. Publishing lifecycle

Staff-approval path:

```text
submitted
   ↓
in_review
   ├── changes_requested
   ├── rejected
   ├── conflict
   └── approved
          ↓
    publishing adapter receipt
          ↓
       published
```

Direct-authorized path:

```text
authorized
    ↓
publishing adapter receipt
    ↓
published
```

Approval/authorization and publication are therefore separate auditable events.

## 9. Publishing receipts

`PublishingReceiptRecord` captures:

- publication request;
- adapter receipt ID;
- publication/deployment reference;
- Site Connection;
- resource;
- exact published revision ID;
- exact published content hash;
- publishing actor/service;
- timestamp.

The receipt is rejected if the current resource head no longer matches the request's target revision/hash.

## 10. Staff CMS surface

Website Platform now contains an **Approvals & Publishing** view with:

- observed resource-head count;
- open customer change requests;
- change conflicts;
- open publication requests;
- publication conflicts;
- application/publishing receipt count;
- Change Request queue;
- staff review actions;
- publication-governance queue;
- explicit concurrency and source-of-truth guidance.

The UI does not create fake customer requests or fake site revisions. Until the Customer Workspace/API adapter phase feeds real records, these queues remain empty.

## 11. Deliberately deferred

V0.17 does not yet implement:

- customer-facing proposal UI;
- connected-site mutation HTTP client;
- connected-site revision observation HTTP client;
- publishing/deployment HTTP client;
- rich visual diff rendering;
- notification delivery for reviewers/requesters;
- production database persistence;
- production authentication/session enforcement.

Those belong to later API/infrastructure/Customer Workspace phases.

## 12. Security guarantees carried forward

V0.17 preserves all earlier restrictions:

- Contract and Site Manifest remain authoritative for technical capability limits;
- V0.16 service entitlements/policy/role/field/security intersection remains the authorization source;
- customer UI is never the security boundary;
- missing policy fails closed;
- stale canonical projections fail closed;
- no canonical Contract IDs are invented;
- staff approval never bypasses optimistic concurrency;
- direct publish still requires current authorization and an execution receipt.
