# V0.15.0 — Contract Registry Resolver Foundation

## Purpose

V0.15.0 introduces the trusted CMS-side boundary required to consume NEXT F Contracts without inventing a parallel contract model.

The approved architecture requires `contracts.nextf.lk` and Contract Version `1.0.0` to remain authoritative for Site Manifests, Modules, Capabilities, Admin metadata, Customer CMS metadata, API operations, exact permissions/scopes, events, webhooks, integrations, validation and compatibility.

## Important source-availability constraint

The CMS archive contains `docs/governance/CMS-CONTRACT-INTEGRATION-GUIDE.md`, but this development environment does **not** contain:

- the Contract Registry `1.0.0` files/snapshot;
- Registry root `AGENTS.md` / Registry `README.md`;
- starter packages or `CMS-MAPPING.json` files;
- an actual managed-site `nextf.site.json`;
- a reachable immutable Registry API/snapshot.

Attempts to resolve `https://contracts.nextf.lk/` from the available execution environment failed because external DNS/network access for the domain was unavailable.

The master plan explicitly states that canonical mapping must not begin without those required inputs. V0.15.0 therefore implements the **resolver infrastructure and trust gates**, but deliberately ships with no fabricated canonical Module, Capability, API, permission, event, webhook, integration, Admin-profile or Customer-CMS-profile IDs.

## Implemented

### Contract Registry evidence model

A Registry snapshot is represented separately from Site Manifest evidence.

Snapshot states:

- `staged`
- `trusted`
- `rejected`

A staged snapshot is never authoritative. A snapshot may be trusted only when verification evidence identifies one of the supported authoritative paths:

- `registry_cli`
- `immutable_registry_api`

Trusted evidence requires:

- exact Contract Version `1.0.0`;
- immutable source reference;
- content hash;
- verification authority;
- verifier identity;
- verification timestamp.

Verifier identity is mandatory. If the CMS already holds trusted immutable evidence for Contract Version `1.0.0`, a later trust receipt with a different content hash is rejected as Registry drift rather than silently replacing the canonical snapshot.

The staff UI intentionally exposes **no manual “trust” button**.

### Site Manifest evidence

Staff can stage exact `nextf.site.json` JSON against a Managed Site Connection. Every receipt creates a new immutable evidence record; receiving a replacement manifest does not overwrite the previous JSON or its validation history. Suspended connections may receive replacement manifest evidence for an explicit re-validation path, while revoked connections remain closed.

Receipt validates only:

- syntactically valid JSON;
- JSON root is an object.

Receipt does **not** claim:

- schema validity;
- Contract Version compatibility;
- known Module IDs;
- known Capability IDs;
- valid Admin/Customer CMS metadata;
- valid API operations;
- valid permissions/scopes;
- valid events/webhooks/integrations.

Those remain unresolved until the official Registry adapter validates them.

### Canonical validation evidence

The CMS now has an explicit evidence model for resolver output. When an official adapter is available, it can persist exact canonical resolution results for:

- Modules;
- Capabilities;
- API operations;
- permissions;
- events;
- webhooks;
- integrations;
- Admin profiles;
- Customer CMS profiles.

Validation fails closed when any of the following occurs:

- schema invalid;
- manifest Contract Version differs from the Site Connection pin;
- compatibility is incompatible;
- unknown Module IDs exist;
- unknown Capability IDs exist;
- resolver issues remain.

The CMS stores the exact canonical IDs supplied by verified resolver output. It does not generate replacement IDs.

Validation output is accepted only while the specific Managed Site Connection and exact Manifest evidence record are already in the `validating` state, and only against the same trusted Registry snapshot bound when validation began. This prevents stale manifests, out-of-order adapter callbacks, or a different snapshot from writing canonical readiness evidence.

## Managed Site Connection lifecycle

The previous `pending / connected / revoked` model is expanded into an explicit validation lifecycle:

```text
registered
   |
   +--> identity_pending
   |
   +--> manifest_received
            |
            v
        validating
        /        \
       v          v
    ready      incompatible
      |             |
      v             +--> re-validation / suspension / revocation
  connected
      |
      +--> suspended
      +--> revoked
```

Legacy V0.12–V0.14 `pending` records are normalized to `registered` rather than deleted.

A Site Connection cannot enter `connected` until it is `ready` and its Site Manifest is canonically `valid`.

## Secret boundary

The UI and documentation reinforce that passwords, API keys, provider tokens and other secrets must never be stored in:

- `nextf.site.json`;
- public Registry content;
- browser-visible resolved metadata.

Production secrets belong in trusted secret storage and future backend adapters.

## Website Platform UI changes

A new **Contracts & Manifests** view shows:

- exact Contract pin;
- Registry source readiness;
- staged/trusted Registry evidence;
- Site Manifest evidence;
- compatibility state;
- canonical validation evidence;
- counts of resolved canonical IDs once official validation exists.

Managed Site Connections now display their lifecycle and contract evidence references.

## What is intentionally not implemented

Because the authoritative Registry snapshot and an actual Site Manifest are unavailable, V0.15.0 does not:

- seed fake Modules or Capabilities;
- seed fake permissions or scopes;
- guess manifest field names beyond accepting raw JSON evidence;
- render Contract-driven customer CMS screens;
- bind customer roles to website permissions;
- activate service entitlements;
- implement Customer Capability Access Policy;
- claim a managed site is canonically compatible.

These remain blocked until real Registry inputs are provided.

## Production adapter contract

The future production adapter should:

1. fetch or load immutable Registry `1.0.0` evidence;
2. verify its immutable reference and content hash;
3. invoke official Registry validation/compatibility logic;
4. call the CMS trusted-snapshot boundary;
5. validate the received `nextf.site.json`;
6. resolve exact canonical IDs;
7. submit canonical validation evidence;
8. allow the Site Connection to become `ready` only on a completely successful result.

## Next phase

Once the real Registry snapshot/API and managed-site manifests are available, finish the canonical resolver binding, then move to **V0.16.0 — Service Entitlements + Customer Capability Access Policy**.
