# CMS v1.0.32 — NEXT F Checkout Payments Control Center (P4 RC)

## Baseline

User-provided CMS v1.0.31 P4 RC.

## Platform Payments

A new first-class `/platform/payments` control plane manages the shared NEXT F Checkout service rather than embedding PayPal/PayHere logic inside Gaming.

The workspace includes:

- Overview;
- Providers;
- Businesses;
- Availability;
- Transactions;
- Webhooks;
- Audit;
- Legacy ledger comparison.

## Providers

CMS can configure non-secret provider state such as environment, Client/Merchant ID, Webhook ID, allowed currencies, display order, enabled/maintenance status and business/market rules. PayPal and PayHere are represented through the Checkout provider abstraction.

Provider secret replacement is write-only and uses a separate server credential + `platform.security.manage` permission. Existing secret plaintext is never returned to the browser and is not stored as readable D1 provider configuration.

## Availability

Payment availability is controlled as:

`provider → business → market → currency`

Rules can enable/disable a method and choose `show_disabled` vs `hide`. Checkout still revalidates all rules server-side, so browser manipulation cannot enable a disallowed provider.

## Business registry

Businesses define allowed HTTPS origins and signed callback URLs. This allows Gaming, `nextf.lk` and future NEXT F businesses to use one Checkout platform without sharing their order/fulfillment databases.

## Permissions

- `platform.read` — Payments read access.
- `platform.settings.manage` — provider/business/availability configuration.
- `platform.security.manage` — write-only provider secret replacement.
- `platform.audit.read` — payment configuration/audit visibility.

## Refund boundary

Checkout has a canonical refund ledger/schema, but CMS v1.0.32 does not expose automated provider-refund execution. Refund automation should be added only when the relevant provider adapter and operational constraints are accepted.

## Deployment

CMS uses server-side bridge credentials `CHECKOUT_ADMIN_TOKEN` and `CHECKOUT_SECRET_ADMIN_TOKEN`; these never enter the browser. Deploy Checkout API first, then CMS API and CMS Pages.

No CMS D1 migration is required for the Checkout control-plane integration.
