# NEXT F CMS v1.0.33 - FazerCards Payment Safety Hardening (P4 RC)

## Purpose

v1.0.33 hardens the v1.0.32 supplier-funding UI using the real FazerCards payment instructions observed before production deployment.

## Changes

- Treats FazerCards `payment.uniqueAmount` (when present) or `payment.amount` as the authoritative amount to send after an invoice is created. It is never reformatted as a USD amount.
- Shows a prominent exact-arrival warning for on-chain USDT payments. The CMS explains that the network fee is separate and the exact provider amount must arrive.
- Adds a copy-amount action that copies the provider decimal string without numeric rounding.
- Generates the payment-address QR code locally in the CMS browser. No address is sent to a third-party QR service.
- Adds a live expiry countdown and locks copy/verify payment actions when the provider payment window has elapsed.
- Keeps status refresh available after local expiry so staff can reconcile the provider state before creating a replacement payment.
- Preserves the exact network, address, memo/tag, provider payment ID and Binance Pay verification flow.

## Security boundaries

`FAZERCARDS_API_KEY` remains exclusive to `nextf-gaming-api`. The browser does not receive supplier credentials. No Binance API key, withdrawal permission, wallet private key or seed phrase is introduced.

Funding still requires both `gaming.suppliers.manage` and `gaming.finance.manage`.

## QR scope

The built-in QR encoder is intentionally limited to payment addresses. It supports QR versions 1-5 at error-correction level M, enough for current TRC20, BEP20, TON and Aptos address lengths. The QR encodes the provider-returned address only and does not invent a wallet URI or destination.
