# NEXT F CMS V1.0.0 — Main Website Project Request Ingestion

Date: 2026-09-14

## Production flow

The canonical project-request path is server-to-server:

1. Visitor submits the real form on `https://nextf.lk`.
2. The `nextf.lk` server route verifies Cloudflare Turnstile using its own server secret.
3. The website builds the contract-shaped `nextf.forms.projectRequest.accepted` payload.
4. The website posts to `POST https://cms-api.nextf.lk/v1/integrations/nextf/project-requests` using a dedicated bearer secret.
5. The CMS Worker verifies the dedicated secret, contract headers, payload relationships, idempotency binding, passed Turnstile evidence and the current live `contracts.nextf.lk` stable production release.
6. CMS stores the full `forms.submission` and `forms.lead` records as private operational D1 documents.
7. CMS projects a staff-only Digital Sales lead into `nextf.v0.4.digital.leads`.
8. CMS records an audit event and emits an identifier-only queue event for downstream integrations.

The browser never receives the CMS integration token or the CMS Worker secret.

## Endpoint

```http
POST https://cms-api.nextf.lk/v1/integrations/nextf/project-requests
Authorization: Bearer <NEXTF_MAIN_SITE_INGEST_TOKEN>
Content-Type: application/json
Idempotency-Key: <submission id>
X-NEXTF-Contract-Version: 1.0.0
X-NEXTF-Event: nextf.forms.projectRequest.accepted
X-NEXTF-Site-Id: nextf-main-website
```

The website must use the same value for:

- `Idempotency-Key`
- `records.submission.idempotencyKey`
- `records.submission.id`

Retries of the same accepted website submission must reuse the same IDs and payload. They must not generate new submission or lead IDs.

## Security boundary

The Cloudflare Access application must bypass **only** this exact integration path:

```text
cms-api.nextf.lk/v1/integrations/nextf/project-requests
```

Do not bypass the full API hostname or `/v1/staff/*`.

The bypass does not make the endpoint anonymous. The Worker independently requires `NEXTF_MAIN_SITE_INGEST_TOKEN` using bearer authentication and fails closed if the secret is missing or wrong.

Use a dedicated integration secret. Do not reuse `SERVICE_CREDENTIAL_SECRET` or the Turnstile secret.

## Worker / website secret pairing

The same random value is configured as:

- CMS Worker secret: `NEXTF_MAIN_SITE_INGEST_TOKEN`
- `nextf.lk` Worker secret: `NEXTF_CMS_API_TOKEN`

The website environment also points to:

```text
NEXTF_CMS_SUBMISSIONS_ENDPOINT=https://cms-api.nextf.lk/v1/integrations/nextf/project-requests
NEXTF_SITE_ID=nextf-main-website
NEXTF_PROJECT_FORM_ID=nextf-project-request
NEXTF_PROJECT_FORM_VERSION=2026-09-14
NEXT_PUBLIC_SITE_URL=https://nextf.lk
```

## Contracts authority

The ingestion Worker does not use an archived local Contracts ZIP as trust authority. For a new ingestion it validates the current live registry metadata at `CONTRACTS_BASE_URL`, requires `status=stable`, requires the live `stableRelease` to match the payload envelope contract version, follows `productionReleaseManifest`, and requires that release to be `STABLE` with zero blocking failures.

The current website handoff pins:

- Envelope: `nextf.forms.projectRequest.accepted@1.0.0`
- Record: `forms.submission@0.9.0`
- Record: `forms.lead@0.9.0`

If the live stable release changes, ingestion fails closed until the website/CMS contract is deliberately upgraded.

## Private data handling

The complete form records are stored under private D1 namespaces:

```text
forms.submission
forms.lead
```

They are not part of `cms.staff-state`, are not included in the CMS durable-state snapshot, and have no public read route.

Only the staff Digital Sales projection is written to:

```text
cms.staff-state / nextf.v0.4.digital.leads
```

The HTTP receipt contains identifiers only. The queue event also contains identifiers only. Raw form PII is not copied into public projections, public endpoints, queue payloads or internal error text.

## Idempotency

The CMS uses durable D1 idempotency keyed by the submission ID.

- Exact completed replay returns the original receipt with `replayed=true`.
- Same key with a changed payload returns `409 IDEMPOTENCY_CONFLICT`.
- Interrupted writes can recover the already-created private records and repair the Digital Sales projection without creating duplicates.
- Failed attempts with no persisted private records may be retried safely with the same key.

## Acceptance

Source validation:

```powershell
npm run check:main-site-ingest
npm run acceptance:source
```

Deployed runtime acceptance additionally requires the dedicated integration token in the operator shell:

```powershell
$env:NEXTF_MAIN_SITE_INGEST_TOKEN = "<same dedicated integration secret>"
npm run acceptance:production:final
Remove-Item Env:NEXTF_MAIN_SITE_INGEST_TOKEN -ErrorAction SilentlyContinue
```

The production acceptance fixture uses private disposable IDs, verifies missing/wrong bearer denial, real acceptance, exact replay, changed-payload conflict, private D1 records, Digital Sales projection and audit evidence, then cleans its own records.
