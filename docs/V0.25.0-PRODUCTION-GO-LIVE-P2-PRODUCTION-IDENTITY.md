# NEXT F CMS V0.25.0 — Production Go-Live P2 · Production Identity

## Goal

P2 removes the local-development staff selector from the production authentication path. Production CMS startup now requires a verified Cloudflare Access assertion, an active exact-subject D1 `staff_identity_bindings` record and the server-authoritative permission set before the React application renders.

## Production startup order

1. `initializeProductionStaffSession()` calls `staff.session.get`.
2. The Worker verifies the Cloudflare Access JWT signature, expiry, issued-at sanity, issuer and configured audience.
3. The verified `sub` and email are resolved against `staff_identity_bindings`.
4. The binding must be active and its stored Access subject must exactly match the JWT subject.
5. The Worker returns the bound staff/account/organization IDs plus the server permission set with `cloudflare-access` assurance.
6. Only after identity succeeds does the frontend initialize the permission-filtered durable D1 state snapshot.
7. `SessionProvider` exposes the verified production principal; local staff switching is not exposed in `production-api` mode.

If any production identity step fails, CMS bootstrap fails closed before application rendering.

## Local development boundary

Local prototype mode intentionally retains the local staff selector so role/navigation development can continue without Cloudflare infrastructure. The selector remains behind an explicit runtime-mode branch, and attempting to invoke impersonation while `production-api` is active throws immediately.

Appearance preference and local prototype persistence are separate local browser concerns and are not production identity sources.

## Cloudflare Access validation

The Worker now treats authentication failures distinctly from internal errors. It validates:

- `cf-access-jwt-assertion` presence and JWT shape;
- RS256 algorithm and signing key;
- cryptographic signature;
- expiration;
- issued-at and not-before timing sanity;
- Access application-token type;
- exact Cloudflare Access issuer;
- configured application audience;
- required `sub` and email identity claims.

The returned assurance is named `cloudflare-access`; the application does not claim that the JWT itself proves a specific MFA method. MFA must be required by the deployed Cloudflare Access policy and proven by deployment acceptance evidence.

## Staff binding bootstrap

The repository includes `npm run staff:binding-sql -- ...` to generate a reviewed D1 upsert for the first/next staff identity binding. The exact Cloudflare Access JWT `sub` must be supplied; P2 does not invent it.

Example shape:

```bash
npm run staff:binding-sql -- \
  --subject '<exact-access-sub>' \
  --email '<staff-email>' \
  --account-id acct_staff_admin \
  --staff-user-id usr_admin \
  --organization-id org_nextf \
  --super-admin
```

Review the generated SQL before executing it against staging or production D1.

## Authorization boundary

Frontend permissions are read from the verified production session only. They control navigation and user experience, but they are not the security boundary: Worker command/query handlers continue to enforce permissions server-side.

Changing a prototype role document alone does not rewrite a production `staff_identity_bindings.permissions_json` value. Production role/binding lifecycle synchronization is deployment/operations work and must remain deliberate until a normalized identity/RBAC model replaces the P1 document bridge.

## Still external after P2

P2 is source-complete identity wiring, not proof of a deployed production identity system. Production V1.0 still requires actual Cloudflare Access application/policy configuration, real staff binding creation, D1 deployment/migrations, dependency build, browser/security smoke, tenant isolation, restore evidence, Contracts/managed-site adapter evidence and the remaining critical acceptance gates.
