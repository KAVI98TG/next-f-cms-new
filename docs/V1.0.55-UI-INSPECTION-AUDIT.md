# NEXT F CMS v1.0.55 — Full UI Inspection Audit

Reference baseline: **Customer Reviews workspace** from v1.0.54. Release parent: **v1.0.54**. Target: **v1.0.55 candidate**.

## Reference pattern

The Reviews workspace is the standard for the internal CMS because it has a clear hierarchy without becoming instructional:

- one page title and one concise purpose sentence;
- summary cards that answer real operator questions;
- one primary workspace for the actual task;
- compact empty-state context only when it explains what will appear there;
- safety/context notes only when they prevent a real mistake;
- readable secondary text instead of dense microcopy.

The goal is not to make every page visually identical. The goal is to make every page obey the same information hierarchy and readability rules.

## Information that stays in the CMS

Keep information when it changes an operator decision or prevents a mistake:

- current status, counts, money, dates, ownership and identifiers;
- actions, search, filters and the fields needed to complete an operation;
- validation errors and required input constraints;
- destructive-action consequences;
- financial warnings, especially exact-arrival amount/network-fee behavior in supplier funding;
- authentication, permission and write-only secret boundaries when they affect what staff can do;
- publishing/billing consequences that are not obvious from the button label;
- integration-unavailable state when it disables an action;
- trust/provenance state when data authority matters;
- concise empty states that explain what record type will appear or what action is available next.

## Information removed from daily UI

The inspection removed or shortened content that belongs in documentation rather than the operating surface:

- global page guides and keyboard-help chrome;
- descriptive sidebar microcopy under every navigation item;
- architecture explanations and implementation commentary;
- release/version history inside operational pages;
- roadmap wording such as foundation, prototype, deferred, future phase and next-step implementation notes;
- tutorial paragraphs that repeat what controls already communicate;
- filler metric-card details added only to occupy space;
- repeated integration explanations when a badge, disabled state or short sentence is enough;
- long modal/form notes that do not affect the action being taken;
- 13 px body/secondary text that created an inconsistent small-text tier.

## Global changes applied

### Shell and navigation

The CMS shell now keeps only global search, theme, notifications and account controls. `PageGuide` and `KeyboardShortcuts` were removed. Sidebar navigation is label/icon-first and no longer renders domain descriptions below every item.

### Typography

The internal CMS now uses a deliberate two-tier lower bound:

- **14 px** for normal secondary copy, metadata, help text and readable supporting information;
- **12 px** only for sparse micro labels such as short uppercase eyebrows or compact machine/status metadata.

Literal **13 px** internal CMS text was removed so new features cannot drift into an in-between small-text tier. Internal text below 12 px is also rejected. The public Gaming storefront remains a separate presentation system and is not changed by this CMS rule.

### Shared components

`MetricCard.detail` is optional. New metrics therefore do not need meaningless footer copy. Existing shared components remain the required starting point for page headers, forms, tables, toolbars, status and state handling.

### Global controls

The existing shared custom checkbox and scrollbar styling remains the source of truth. Feature pages should not recreate native-looking controls or page-local scrollbar styling unless the global component/system genuinely cannot support the requirement.

## Area-by-area inspection

### Platform

Page introductions across Accounts, Audit, Backup, Cleanup, Data Management, Domains, Health, Help Center, Identity, Infrastructure, Integrations, Logs, Notifications, Organizations, Payments, Roles, Security, Settings and Users were reviewed for operational relevance.

Developer-oriented wording was replaced with concise state/action language. Infrastructure cards now present the service, purpose and current status instead of implementation-history labels. Security and Settings retain Cloudflare Access authority because it changes where production authentication policy is managed, while local development wording is kept short. Backup/Data Management retain D1 Time Travel because it is the actual production recovery path.

### NEXT F Digital

Dashboard, Clients, Sales, Projects, Services, Billing, Sites, Support, Reports, Automation, Settings and Website Platform headers were reduced to short task-focused descriptions. Lead/proposal forms no longer carry tutorial-style copy. Site health actions no longer describe local sandbox implementation details.

Website Platform received the largest content reduction: tutorial-style governance/lifecycle cards and historical implementation wording were removed, while contract validation, customer capability limits, publication state, acceptance gates and destructive/financial consequences remain because they affect real operator decisions.

### Gaming Store

Dashboard, Orders, Suppliers, Pricing, Catalog, Customers, Finance, Promotions, Analytics, Support, Settings and Storefront Merchandising were reviewed. Supplier architecture explanation was removed, but credential protection and supplier-funding safety remain. The exact-arrival/network-fee warning is intentionally retained because removing it could cause a financial error.

Customer Reviews remains the visual/content reference: short page context, meaningful metrics, focused moderation workspace, concise empty state and a single verified-purchase protection note.

### Software

Dashboard, Products, Releases, Customers, Orders, Licenses, Subscriptions, Downloads, Updates, Support, Analytics and Settings were reviewed. Page descriptions now identify the task or data being managed rather than explaining data-model separation or future infrastructure work. Integration-unavailable states remain only where they directly disable an action.

## Content that must not be removed in future cleanup

Minimal UI does not mean removing safety-critical context. Keep these classes of information even when they add a sentence:

- supplier funding exact-arrival amount and separate network/withdrawal fee;
- production authentication/access authority;
- write-only secret behavior;
- production recovery path and destructive restore/delete consequences;
- billing or publishing consequences that are not automatic/obvious;
- permission or customer-visibility consequences;
- rejected-review privacy state;
- unavailable-integration reason when it blocks an action.

## Future guardrails

`docs/CMS-UI-CONTENT-AND-TYPOGRAPHY-STANDARD.md` is the implementation standard for new sections. Automated checks now protect the same decisions:

- `npm run check:ui-hygiene` rejects guide/help regression, sidebar description regression, overly long page descriptions and visible developer/roadmap copy in common UI copy locations;
- `npm run check:font-floor` rejects internal text below 12 px and the 13 px tier;
- `npm run check:global-ui` protects shared UI behavior;
- `npm run check:all-static` runs the full static `check:*` suite;
- `npm run release:finalize` must pass the static suite, release gate, frontend build and Worker/API typecheck before `RELEASE-STATE.json` becomes canonical.

## Release status

v1.0.55 is intentionally packaged first as an **exact-parent candidate patch from v1.0.54**. No D1 migration, Worker API contract change or secret addition is part of this UI release. A full canonical ZIP should be created only after `npm run release:finalize` succeeds in an environment with a complete dependency install.
